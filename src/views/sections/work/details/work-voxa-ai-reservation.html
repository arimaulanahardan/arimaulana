Voxa: an AI phone receptionist that books appointments

A salon chain in Japan kept losing bookings for one simple reason: the phone rang while everyone was busy with a client, or after closing. So we put an AI on the line. It picks up, understands what the caller wants, checks the booking rules, reads the booking back, and logs every call with its recording and transcript for the staff to review.

The problem

A salon lives on its booking calendar, and most bookings still come in by phone. When a stylist is halfway through a color job, nobody picks up. When the shop is closed on Monday, nobody picks up. Every one of those missed calls is a customer who probably books somewhere else.

The ask was simple to say and hard to build: answer every call in natural spoken Japanese, take new bookings, changes and cancellations, never promise a slot that doesn't exist, and give the 1 to 3 staff per store a clean place to check what happened on each call.

The architecture

Here's the whole thing on one page. The caller dials the salon number, Twilio streams the live audio to our Fastify backend, and the backend bridges it to the OpenAI Realtime API. Speech goes in, the model reasons and calls our tools, speech comes back out. No robotic menu, no "press 1". Every call lands in PostgreSQL, and the staff review them in the admin panel.

The hard parts, and how I solved them

Putting an AI on a phone line sounds easy until a real person calls. These are the problems that took actual engineering.

  • Silence kills a phone call. On a website, a two second wait is fine. On the phone it sounds like the line dropped, and people hang up. So I kept the audio in Twilio's native μ-law format end to end with no conversion step, used the Realtime API so speech goes straight in and straight out, and trimmed the prompt down to just the current task once the AI knows what the caller wants. Fewer tokens per turn, faster replies.
  • Real callers interrupt, and change their mind. Nobody waits politely for a bot to finish. Semantic voice activity detection works out when someone actually finished a sentence, and the moment the caller starts talking, the AI stops. If the caller corrects the booking, the AI takes the correction, up to three times. After that it ends the call politely and logs it for staff to follow up, instead of looping forever.
  • Language models love to say yes. The scariest bug in a booking bot is "you're all set!" when nothing was booked. So the system won't let the AI report success unless the confirm tool actually ran. If it didn't, the call is logged as failed with a reason the staff can read and act on.
  • Names and numbers over a phone line. Japanese names, phone numbers, dates, all spoken over a cheap phone line. The AI finds a free slot first and only then asks for a name and number, so nobody spells their name for a time that isn't available. Then comes a two turn read back: the AI repeats everything, asks "is that correct?", and waits for a clear yes.
  • Rules that can't bend. Closed days, opening hours, a 30 minute slot grid, at least 60 minutes notice for same day bookings, up to 7 days ahead. These live in code, not in the prompt, so the AI can't talk its way around them. When a request breaks a rule, the caller always hears alternatives instead of a flat no, and availability is checked one last time right before confirming.

How I write the code

I try to write code the next engineer can read without calling me. In practice that means a few habits I don't skip.

  • TypeScript in strict mode everywhere. Unused code fails the type check, so dead code doesn't pile up.
  • Validate everything that comes from outside. Forms, URL parameters and environment variables all go through Zod. A broken link like ?page=abc falls back to page 1 instead of crashing the screen.
  • Every screen has all its states. Loading, empty, error, and the happy path. The call log list alone has a skeleton loader, an empty row, an error row with retry, and pagination for 10, 20, 50 or 100 rows.
  • Errors a human can understand. A failed call doesn't just say "error". It says the caller hung up before the booking was confirmed, so the staff knows to call them back.
  • Small commits with clear names. One feature per branch, Conventional Commits like feat(call-logs) or fix(ui), merged without squashing so the history tells the story of the build.

The process, step by step

I use a method I call ATM, which in Indonesian stands for Amati, Tiru, Modifikasi: observe, imitate, modify. You study what already works, rebuild it faithfully, and only then change things on purpose.

  • 1
    Observe. I read the original end to end and wrote it all down: screens, call flow, business rules, API shapes, design tokens. Before writing a single line, I knew exactly what "done" meant.
  • 2
    Design first. Every screen and every state got designed before code, including the date picker open, the failed call and the 404 page.
  • 3
    Plan in stages with a dependency map. Setup, login, app shell, call logs, call detail, system pages, landing page, final check. Each stage has its own branch and can't start until the one it depends on is verified.
  • 4
    Build with AI agents, review like a lead. I run AI coding agents in parallel, each in its own git worktree. My job is the one a tech lead has: split the work, check each stage against the design, and only then merge. The agents type fast. I'm the one who says what's good enough.
  • 5
    Prove it with screenshots. Every stage left evidence behind: 74 screenshots across desktop, tablet and phone, plus a final report of 18 screen and state checks. All 18 passed, with type check and build both clean.

Security, and how I checked it

A phone line that can create bookings is a door into the business, so I treat it like one. This is what the original system does:

  • Only Twilio can talk to the voice endpoint. Every request, both the HTTP webhook and the live audio socket, has its Twilio signature verified. A fake request gets dropped.
  • Staff login done properly. Passwords hashed with argon2. The session lives in a signed, httpOnly, SameSite strict cookie backed by a session row in the database, so it can be revoked. Requests from other origins are rejected.
  • Rate limits and security headers on every route, including a Content Security Policy.
  • Customer data stays private, even from staff. Phone numbers come out of the API masked to the last 4 digits, and sensitive fields are redacted from the server logs.

And in the rebuild itself: the login redirect blocks open redirect tricks (javascript:, data:, protocol relative and cross origin URLs), every route behind login has a guard, and a 401 anywhere clears the session and sends you back to login. I also took the client and vendor names out of every public file, and kept my own analysis of the original out of the repo entirely.

Performance, measured

The voice side is tuned for short turns, as you read above. For the web side, I don't want you to take my word for it, so I ran Google Lighthouse against the live demo.

  • Landing page: 100 out of 100 in all four Lighthouse categories on desktop, performance, accessibility, best practices and SEO. On a mobile profile, performance still scores 99.
  • The page is on screen in 0.3 seconds on desktop (largest contentful paint), and in 1.1 seconds on a throttled mobile connection.
  • 42 KB for the whole page. It's static Astro with almost no JavaScript, so there's nothing heavy to download. Most websites ship more than that in fonts alone.
  • The admin panel feels instant. Pages preload when you hover a link and recordings are cached after the first play. Even on a mobile profile it scores 91 for performance with 100 for accessibility.

Delivery

The original ran as a working PoC on AWS in Tokyo: the backend in a container on ECS, PostgreSQL next to it, secrets in SSM Parameter Store, and GitHub Actions running lint, type check and tests on every pull request, then deploying automatically once the code is merged. The rebuild is split into two apps, each one its own Vercel project deployed straight from main. Every change goes out the same way and can be rolled back in one click.
