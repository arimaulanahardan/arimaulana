A network benchmark dashboard: where a mobile operator wins and loses, city by city

A national mobile operator in Indonesia needed one answer every week: in which cities is our network better than the other three operators, where are we losing, and why. I built the dashboard that answers it, from a nationwide map down to the single site that needs fixing.

Client
National mobile operator (Indonesia)
My Role
Full stack engineer, built the API and the dashboard end to end
Timeline

Tech Stack
React, TypeScript, Mapbox, ECharts, Redux, Ant Design

The problem

In telecom, customers don't compare coverage maps. They compare how their phone feels: does the video buffer, does the game lag, is the download fast. Independent firms like Tutela and Open Signal measure exactly that, using tests that run on real phones across the country, for every operator.

So the data existed. What the operator's teams needed was a way to act on it. Four operators, hundreds of cities, 13 regions, 9 quality metrics, every week, measured against quarterly targets. Each regional team had to know three things fast: which of our cities are losing, what exactly is making them lose, and is it getting better or worse.

What the dashboard answers

  • "Where are we winning?" The summary page colors every city on the map: green when the operator wins all services, yellow or orange when it wins only some, red when it loses everything. Next to it, a table per region shows this week against last week and against the quarterly target, and a chart ranks where the biggest opportunities for improvement are.
  • "Why did we lose there?" The fail contributor page breaks a loss down by metric: latency, packet loss, jitter, download or upload speed. You can drill from region to regency to district, weekly or monthly, as numbers or percentages, for any operator.
  • "Is it stable, or just luck this week?" Some cities flip between winning and losing every few weeks. The flip flop page finds them, plots each operator against its upper and lower bands and moving average, and lists the exact sites with bad samples, so the field team knows which tower to look at.
  • "How is it trending?" Daily, weekly and monthly trends for each metric, nationwide, by region or by city, plus the OKR achievement line against its target. Charts and tables can be exported to CSV for the weekly report.

The architecture

Real phones run speed, video and game tests. Tutela and Open Signal collect them. I built both sides from there: the API that turns those results into scores per city, region and week, and the dashboard on top of it, with a filter bar, a store that remembers the view, and the map, charts and tables that turn those scores into a decision.

The hard parts, and how I solved them

  • Hundreds of cities on one map, still readable. Indonesia has more than 500 cities and regencies. I drew each one as its real boundary and colored it with just four states, so a manager sees the whole country at a glance. The legend counts each state, and clicking a city shows which service it won or lost, and to which competitor.
  • Too many charts, too little time. Nobody in a weekly meeting reads twelve charts. Under every KPI chart the dashboard writes the takeaway in plain words, like how many cities were won this week and which three regions are at the bottom. Read one sentence, then look at the chart only if you need to.
  • Lots of filters, nobody wants to set them twice. Data source, view, week, region, city. The dashboard remembers your last selection, so when a regional lead opens it on Monday, it comes back on the view they used last time.
  • Building both sides at the same time. Every one of the 40+ data endpoints got a realistic mock response first, so the screens could be built and reviewed while the API behind them was still being finished. Switching to the real data needed no change to the screens.
  • Two data vendors, one way of reading them. Tutela and Open Signal measure things a bit differently. Instead of two separate tools, the team switches the source from one dropdown and keeps the same map, table and charts they already know.

How I write the code

  • One folder per feature. Map, KPI, fail contributor, flip flop: each has its own services, mock data, hooks and components. A new developer can work on one page without reading the whole app.
  • TypeScript in strict mode. Every API response has a type, so a renamed field breaks the build instead of quietly showing a blank chart.
  • Tests on the numbers. The functions that turn raw data into what you see on the map and in the charts have unit tests, because a wrong color on a city is a wrong decision.
  • Built on the company's shared libraries. Maps, charts and the API layer come from the team's internal packages, so this dashboard looks and behaves like the rest of their tools.

Fast enough for a live meeting

This dashboard gets opened on a big screen with the whole team watching. If it hesitates, people stop trusting it.

  • Only loads what you're looking at. Changing a filter fetches the data for that view, not the whole database.
  • Search that waits for you. City and district search waits until you stop typing before it asks the server, so typing a long name doesn't fire twenty requests.
  • No jumping layout. Placeholders hold the shape of each chart while it loads, and charts only redraw when their own data changes.

Delivery

The build packages the whole dashboard into a single file, ready to drop onto the client's own server under its own path, next to their other internal tools. No new infrastructure for their team to manage.
