The problem

For an app, the landing site is the shop window. Most visitors arrive from a Google search on their phone, decide in a few seconds, and leave if the page is slow, jumps around while loading, or looks broken at their screen size. A beautiful design only pays off if it survives that.

The brief: take a finished design for a finance app's site and ship it as real code. It had to match the design on every screen size, keep all of its animation, load fast, and be set up so Google can find and understand every page. And it had to be easy to change later, without a page builder or a monthly CMS bill.

What I built

  • A complete marketing site, 46 pages. Home, features, pricing with a monthly and yearly switch and a plan comparison table, about with the team and open jobs, a blog with 10 articles, integrations, a changelog, download, contact and the legal pages. One set of colors, type and components runs through all of it.
  • Matched to the design on every screen. Phones, tablets and laptops each have their own layout, and each one was checked side by side against the design until spacing and type lined up.
  • Motion that feels like a premium app. A short intro on first load, sections that glide in as you scroll, phones that drift with parallax, stacked cards that pin as you pass them, scrolling tickers, letters that roll on hover and smooth scrolling.
  • Set up for Google from day one. Every page has its own title, description and canonical address. There's a sitemap, a robots file, structured data that describes the company, the app with its three plans and every article, and a proper preview card when a link is shared.
  • Content you can change without touching the design. Prices, articles, jobs, team members and integrations live in 14 typed content files. Change a price or add an article there, and every page that shows it updates.

The stack

Every page is built once, when the site is deployed, and served as a ready made file from Vercel's network. There's no server working out a page while the visitor waits, and nothing to keep running or patch. GitHub Actions checks every change before it goes out.

The hard parts, and how I solved them

A landing page looks simple in a screenshot. Making it match a design at every size, move smoothly and still rank is where the work is.

  • Matching the design at three sizes, not one. Designs are usually perfect at one width and guesswork at the others. I captured the design at phone, tablet and laptop width, set colors, type and spacing as shared tokens, then compared every section screenshot to screenshot at each size and fixed what didn't line up.
  • Rich animation without a jumpy page. Lots of motion usually means content that shifts while it loads, which annoys visitors and costs ranking. Every image and section keeps its space from the first paint, and the fonts are served from the site itself and loaded early. Lighthouse measures the layout shift at almost zero.
  • Google sees what people see. The first version had the same title and description on every page and no sitemap, so Google would have seen 46 copies of one page. Now each page describes itself, and the structured data is built from the same files as the page, so the prices Google reads are always the prices on the page.
  • Easy to edit, without a CMS bill. A small marketing team doesn't need a paid CMS on day one. All the copy lives in typed files, so a missing price or a misspelled field stops the build instead of breaking the live page, and an address that doesn't exist shows the 404 page instead of an empty one.

How I write the code

  • One component per section. 72 small components on top of shared tokens and parts, so a new page is mostly putting existing sections together.
  • Checked on every push. GitHub Actions runs the linter, the TypeScript check and a full build before anything can go live.
  • Not locked to one host. It runs on Vercel today, and the same code also ships as a Docker image, so it can move to your own server if you ever want to.
  • Clean history. Small commits, each describing one change, with strict TypeScript across the project.
